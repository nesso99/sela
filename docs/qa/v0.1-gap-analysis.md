# Sela v0.1.0 gap analysis

Candidate: `73ae3d8` (M1, PRs #9–#26). This file maps each M1 acceptance criterion to the automated test that covers it, or to `manual-only` or `not covered`. The test plan is [v0.1-test-plan.md](./v0.1-test-plan.md).

“Covered” means a crate test or a `db-integration` / `db-tls-postgres` job asserts the observable behavior. A test that only maps an enum, or that skips unless an env var is set, is named so. `manual-only` means a person at a display has to judge it. `not covered` means nothing asserts it, including the manual checklist’s first execution (the checklist now lists it, but no run has passed yet).

Paths are under `crates/`. Integration tests live in the driver files and run in CI job `db-integration` when `SELA_POSTGRES_URL` and `SELA_MYSQL_URL` are set, or in `db-tls-postgres` for the TLS names.

## Top 5 missing automated tests

Ranked by risk if v0.1.0 ships without them. Another engineer should implement them. They are not in this PR. Tests 1 and 2 fail on `73ae3d8` if written to the contract; that failure is the bug, not a bad test.

### 1. MySQL `IDENTIFIED WITH <plugin> BY` is not stored in history

- **Risk:** A database password lands in plaintext `history.sqlite`. The forms the unit test already lists are skipped; the usual MySQL 8 plugin clause is not, because `IDENTIFIED` and `BY` are not adjacent and `mysql_native_password` is a single word.
- **Asserts:** `history_sql_contains_password_clause` is true, and `should_record_history_sql` is false, for:
  - `CREATE USER 'u'@'%' IDENTIFIED WITH mysql_native_password BY 'secret'`
  - `ALTER USER 'u'@'%' IDENTIFIED WITH mysql_native_password BY 'secret'`
  - `CREATE USER 'u'@'%' IDENTIFIED WITH caching_sha2_password BY 'secret'` (MySQL 8 default plugin; the digit split yields `_password`, which must still count)
  - `CREATE USER u IDENTIFIED WITH auth_plugin BY 'secret'` (plugin name does not contain the word `password`)
  - Still false for `SELECT password_hash FROM users`, for the same DDL inside a `--` comment or a string literal, and for `CREATE TABLE t (password text)`.
- **Where:** `crates/sela-core/src/history.rs`, next to `password_setting_ddl_is_not_recorded`. The store does not need a new test; it only inserts what the app passes. Optional follow-through: one `sela-config` test is unnecessary if the helper is the gate.
- **Approach:** Table-driven strings. No database. Extend the blank-and-tokenize matcher so `IDENTIFIED … BY` counts even with words between them, without flagging `IDENTIFIED BY` inside comments (the blanker already exists). Do not redact; skip the row.

### 2. Menu `LIKE` escape matches a literal `%`, `_`, and `!` on all three engines

- **Risk:** The operator the filter menu offers cannot find a literal percent or underscore, while the tooltip says `use ! to escape`. Users get the wrong row set. Contains (legacy, not in the menu) is already correct.
- **Asserts:**
  - `FilterOp::Like` value `100!%` binds a pattern that matches only `100%` under `ESCAPE '!'`.
  - Value `a!_b` matches only `a_b`.
  - Value `wow!!` matches only `wow!`.
  - Value `%` matches every non-null name (wildcards stay wildcards).
  - The SQL text contains `LIKE` / `NOT LIKE` and `ESCAPE '!'`, uses a placeholder, and does not contain the user text. Postgres menu `LIKE` is not `ILIKE`.
  - Empty pattern is `Err` and builds no statement.
- **Where:** Change the expectation in `sela-core/src/filter.rs` `validate_empty_text_eq_and_reject_null_literal_on_int` (today it expects `a%!b` → `a%!!b`). Add execution to `sqlite.rs` `filter_and_sort_bound_params_with_special_chars`, `postgres.rs` `postgres_filter_and_sort_when_configured`, and `mysql.rs` `mysql_filter_and_sort_when_configured`. Those tests already insert `100%`, `a_b`, and `wow!`.
- **Approach:** Bind `escape` so a user-typed `!` is the escape character, not a character that is always escaped again. Keep doubling inside **contains / starts / ends**, which treat the whole value as a literal. Run the three engine tests with the URLs set so a skip cannot hide a mismatch.

### 3. Run-all stops on the first error, and cancel does not start the rest

- **Risk:** A later `INSERT`/`CREATE`/`DELETE` runs after a failed statement, or after the user hit Stop. That is the data-loss case in a read-only client.
- **Asserts:** Given the queue `["SELECT 1", "SELECT boom", "CREATE TABLE sela_should_not_exist (id int)"]` and a failure on the second item, the third is never started. Given a cancel on the first item, the second is never started. Successful items before the failure are kept, in order, and the failed index is 2. More than 8 successes retain the latest 8.
- **Where:** New pure helper in `crates/sela-core/src/sql.rs` (or `sql_batch.rs`), called from `sela-app/src/ui/workspace/query.rs` `finish_sql_statement` / `apply_cancelled`. Do not require GPUI.
- **Approach:** A tiny state machine: `on_finished(queue, outcome) -> Stop | Continue(next)`. Unit-test it with scripted outcomes. Optionally one SQLite test that runs the same three strings through `run_user_sql` only if the helper says continue, and asserts the table was not created. Leave the GPUI strip paint as manual.

### 4. TLS negatives: bad CA, TLS required against a plaintext server, `prefer` fallback, MySQL verify-full

- **Risk:** `verify-full` accepts the wrong certificate, or `require` silently uses plaintext, or the default `prefer` fails closed on the Docker sample servers and blocks first-run. Postgres CI never tries a bad CA or a TLS-off server. MySQL has no live TLS job.
- **Asserts:**
  - `verify-ca` and `verify-full` with a CA that did not sign the server → `Err(DbError::Tls)`.
  - `require` against Postgres 16 and MySQL 8.4 with TLS off → error, and not a successful `list_schemas`.
  - `prefer` against those same plaintext servers → success.
  - MySQL `verify-ca` to an address absent from the SAN, with the right CA → success.
  - MySQL `verify-full` to that address → `DbError::Tls`.
- **Where:** Extend `crates/sela-drivers/tests/postgres_tls.rs`. Add `crates/sela-drivers/tests/mysql_tls.rs`. CI: extend `db-tls-postgres` with a second plaintext container or a mode flip, and add `db-tls-mysql` (generate a server cert in the job, never commit it). Skip when the env vars are unset, fail when they are set and the server is down. Same rule as today.
- **Approach:** Reuse `scripts/gen-pg-tls-certs.sh` for the “wrong CA” file (a second output directory). For MySQL, `openssl` in the job plus `require_secure_transport` off so `prefer` and `require` can both be pointed at known configs. Call `sela_drivers::connect`, not a hand-rolled sqlx pool, so `DbError` mapping stays on the real path.

### 5. Caret vs selection vs run-all chooses the right statement text

- **Risk:** Secondary+Enter runs every statement, or runs a fragment of a `$body$` function, or splits on a semicolon inside a string. The splitter is tested; the choice of *which slice* is entirely in `statements_for_run` and has no test.
- **Asserts:** A pure function `statements_to_run(sql, dialect, selection) -> Result<Vec<String>, SqlError>`:
  - Empty selection, caret in the second statement → only that statement.
  - Caret in a leading `--` comment → the first statement.
  - Selection covering two statements → both, in order.
  - Selection that is only `'a;b'` → one statement.
  - Postgres selection that sits inside `$body$ … ; … $body$` → one statement.
  - Unclosed quote → `SqlError::UnclosedQuote` with the opening offset.
  - Run-all is `split_statements` of the whole buffer (already tested; call it from the same helper with a full-range selection so the app cannot drift).
- **Where:** `crates/sela-core/src/sql.rs`, next to `statement_index_at`. `sela-app/src/ui/workspace/sql_run.rs` should call it instead of reimplementing the branch. No GPUI in the test.
- **Approach:** String fixtures and byte ranges. Keep `statement_index_at` as the caret primitive. Add one live Postgres test only if the pure test cannot construct the `$body$` case; it can, the existing dollar-quote tests already do.

## Not in the top 5, on purpose

Quit (TC-QUIT-01..07) is the highest **product** risk and a release blocker, but it is a window-lifecycle and focus test. CI has no display, and gpui’s test harness does not prove Fedora Wayland close buttons. It stays on the manual checklist. A pure `quit_decision(query_running, choice)` helper would be cheap later; it would not have caught “Ctrl+Q is unbound”.

Visual theme contrast, IME, and cold-start timing stay manual or on the M4 benchmark follow-up.
